## 第2回：変数化 〜ハードコードをやめる〜
📅 2026-07-29

**この回のテーマ**
`variables.tf` に `instance_type` / `region` / `vpc_cidr_block` / `subnets` / `project_name` を切り出し。共通タグは `locals` + provider の `default_tags` で一括付与。

**つまずき**
`locals` と `merge()` を**同時に**説明されて詰まった。ここで「1回に新概念は1つまで」という進め方が定着した。

**腑に落ちた瞬間**
`default` は「固定値」ではなく **「未指定時のフォールバック」＝省略を許すかの設計判断**。そして **variable=利用者が決める入力 / data=AWSが決める事実 / locals=コードが作る中間値 / resource=作るもの**、という「値の決定権は誰が持つか」の軸。

**面接で使える一言**
「タグは `default_tags` で共通化し、各リソースは `Name` だけ持たせた。管理タグを一箇所で変えられる。」

**🔑 深掘り用キーワード**
default=フォールバック / 変数の優先順位（-var > tfvars > TF_VAR_ > default）/ 補間 `"${}"` / default に変数不可→locals

## 第3回：for_each で複数AZ 〜count との違い〜
📅 2026-07-29

**この回のテーマ**
サブネットと route table association を `for_each = var.subnets` で複数AZ化。`apply` で13リソース作成。

**面接で使える一言**

**🔑 深掘り用キーワード**

## 第8回：プライベートサブネット＋VPCエンドポイント化 〜インターネット無しでSSM〜
📅 2026-08-04

**この回のテーマ**
EC2から Public IP も IGW も無くし、**インターネット非接続のまま**SSMでシェルに入れることを実証。SSMに必要なインターフェイスエンドポイント3つ（`ssm` / `ssmmessages` / `ec2messages`）を作る。

**つまずき**
「PrivateLink＝EC2への接続手段」と誤解し、SSHやVPNと混同して長く迷った。他にも `protocol` と `port` の混同（443はポート、tcpがプロトコル）、マップ→set の自動変換、`subnet_ids` の取り違え、`vpc_id = var.vpc_cidr_block`（validateは通るがapplyで失敗する型の取り違え）。

**腑に落ちた瞬間**
**PrivateLinkは「サービスへの道」であって「EC2への道」ではない**（EC2へはIP or SSM）。**SGとサブネットが要るのはENIがあるから**——Interface型はENI有り（SG/subnet要）、Gateway型はENI無し（不要・無料）。`private_dns_enabled=true` は「標準のDNS名の"解決先"をエンドポイントのprivate IPに変える」設定。EC2→エンドポイントは**localルート**が運ぶ（エンドポイントもVPC内のリソースだから）。

**面接で使える一言**
「Public IPもIGWも持たない（インターネット到達不能な）EC2に、VPCインターフェイスエンドポイント経由でSSMエージェントを登録させ、instance-id指定でシェルを確立。SSMがアウトバウンド通信であることを閉域ネットワークで実証した。」

**🔑 深掘り用キーワード**
Interface vs Gateway（ENIの有無で全部決まる）/ PrivateLink=サービス窓口・EC2へはSSM / private_dns=DNS解決先の変更 / localルートがエンドポイントへの道 / SSMは3エンドポイント / エンドポイントはサービス単位・VPC共有 / SGはステートフル（受信=送信の返り）/ NATとのコストトレードオフ / 実証：Public IP=null・PingStatus=Online

## 第9回：3層Webアプリ化 ─ ALB導入 〜公開層を戻し、privateなEC2をネットに公開する〜
📅 2026-08-05

**この回のテーマ**
第8回で削った公開層（IGW＋パブリックサブネット）を復活させ、ALB（Application Load Balancer）を前段に置いて「インターネット → ALB(公開) → EC2(非公開)」の3層Webアプリ構成を作る。EC2はパブリックIPを持たないまま、ALB経由でWebページをネットに公開。httpdはS3ゲートウェイエンドポイント経由でインストール。

**つまずき**
ALBが新規サービスすぎて各引数の意味が全く分からず、概念の寄り道が大量発生（OSI層・エンドポイント・DNS・ミドルウェアまで遡って質問）。実装ミスも多数：ELB名にアンダースコア不可（DNSホスト名になるから）、リスナーの`target_group_arn`欠落、`enable_deletion_protection=true`でdestroy不可、S3 Gatewayに`subnet_ids`等のInterface専用引数を書いてエラー、for_eachに別サービス`s3tables`混入。outputを`.name`のままapplyして`test-alb`が出た（`.dns_name`が正解）。

**腑に落ちた瞬間**
ALBは「本体＋ターゲットグループ＋リスナー」の3点セットで1つの仕組み。SGのソース指定は「相手がSGを持つAWSリソースか」で`security_groups`(SG参照)か`cidr_blocks`か決まる（ALBのIPは動的なのでSG参照）。EC2のSGとALBのSGは重複でなく多層防御（信頼は伝播しない・ALBは送信元IPを付け替える）。ALB→EC2もSSMも同じ**localルート**が運ぶ。Interface(ENIあり=localルート)とGateway(ENIなし=専用ルート)。ミドルウェア＝OSとアプリの間の土台製品。OSI層の判断軸（L3/L4/L7）で通信を整理できる。

**面接で使える一言**
「パブリックIPを持たないプライベートサブネットのEC2を、公開層のALB経由でインターネットに公開。ALBがL7で受けてlocalルートでprivate IPのEC2へ転送し、EC2のSGはALBのSGからのみ許可する多層防御を構成。httpdはNAT無しでS3ゲートウェイエンドポイント経由で導入し、HTTP 200・target healthy・privateなホスト名(ip-10-0-1-251)を返すページを実機確認した。」

**🔑 深掘り用キーワード**
ALB3点セット（本体/TG/リスナー）/ ALB(L7)vs NLB(L4) / SGソース=cidr_blocks/security_groups/prefix_list_ids / SG参照はIP非依存 / 多層防御（信頼は伝播しない）/ 可用性2階建て（ALBマルチAZ＋ターゲット分散＝次のASG）/ クロスゾーン負荷分散 / localルートが全通信の土台 / Interface(local)vs Gateway(専用ルート・逃がさないため) / ELB名はDNSホスト名でアンダースコア不可 / user_data=起動時スクリプト / ミドルウェア=OSとアプリの間の土台 / OSI7層(L=Layer・Interconnection)

## 第10回：Auto Scaling 導入 〜自己修復するインフラと「家畜」の思想〜
📅 2026-08-06

**この回のテーマ**
固定1台の `aws_instance` を捨て、`aws_launch_template` ＋ `aws_autoscaling_group` に置き換える。ASGがAZ-a / AZ-c に1台ずつEC2を起動し、ALBのターゲットグループへ自動登録。`health_check_type = "ELB"` を設定し、**httpdを手で殺してASGが自動でEC2を作り直すところまで実機で観察**した。

**つまずき**
前セッションで書いたASGコードが**Ctrl+S忘れで消失**（第4回の再演）。会話ログのjsonlから復元して再開した。`plan` のリソース数予測で「ASGが起動するEC2 2台」を数えて28と答えてしまった（正解は27）。「調査したい1台を生かす仕組み」を `health_check_type` と誤答（正解はスタンバイ）。壊した1台が `shutting-down` に入るまで**ずっと `running` に見える**ことに混乱した。

**腑に落ちた瞬間**
Terraformが作るのは「**ASGという箱**」までで、EC2はASGが作るので **stateにもplanにも出ない**。ASGの行動ログにその瞬間が残っていた ─ `06:06:46 a user request created an AutoScalingGroup`（Terraformの仕事はここで終わり）→ `06:06:48 an instance was started in response to a difference between desired and actual capacity`（ここからはAWSの仕事）。だから `output "instance_id"` は書けなくなり、個体はNameタグで探すものになる＝**Cattle, not Pets**。そして自己修復の決定的証拠が `an instance was taken out of service in response to an **ELB system health check failure**`。既定の `"EC2"` のままなら、OSは生きているのでこの行は永久に出ない。

**面接で使える一言**
「固定EC2をASG化し、ELBヘルスチェック連動で自己修復する構成にした。ASG配下のEC2はTerraformが作らないためstateに載らず、インスタンスIDをoutputできない。これは個体を手当てせず入れ替える運用（Cattle, not Pets）への転換そのもの。実機でhttpdを停止させ、ALBが約60秒で切り離し、その後ASGが該当インスタンスを終了して別IPの代替を起動するまでをスケーリングアクティビティのログで確認した。可用性とは障害をゼロにすることではなく、検知と復旧に要する時間を短くすることだと説明できる。」

**🔑 深掘り用キーワード**
launch_template ＝ EC2の設計図 / ASGは箱・EC2はAWSが作る（planに出ない）/ 結合点は `target_group_arns` の1行（ALBはASGを知らない）/ `health_check_type = "ELB"` が自己修復の前提 / desired=エンジン・min=床・max=天井 / 検知は瞬時でない（interval 30秒 × unhealthy 2回 = 最大60秒）/ 速い検知 vs 誤検知のトレードオフ / ALBは切り離すだけ・殺すのはASG / Cattle, not Pets / スタンバイはコードでなくCLI（Terraformは名詞・CLIは動詞）/ `describe-scaling-activities` の Cause が一次ソース / 読むのは自由・書くのはTerraformだけ（drift）/ ログの3層（CloudTrail＝APIの玄関 / ASGアクティビティ / インスタンス内）/ CloudTrailのイベント履歴(既定ON・90日)と証跡(作る・無期限)

## 第11回：ヘルスチェックの明示化 〜インフラを1ミリも変えずにコードを変える〜
📅 2026-08-10

**この回のテーマ**
第10回で「最大60秒で切り離される」ことを実機で確認したのに、`aws_lb_target_group` には `health_check` ブロックが1行も書かれていなかった。60秒はAWSの既定値がたまたまそうだっただけで、自分が決めた値ではない。**暗黙の既定値への依存を、明示的な設計判断に変える**のがこの回の目的。値は既定と同じにしたので、AWS側の実態は何も変わらない。

**つまずき**
`healthy_threshold` を「不健康と判定する回数」と取り違えた（正解は復帰に必要な連続成功回数で、60秒を作っていたのは `unhealthy_threshold`）。`path` に **`/var/www/html/index.html`（サーバー内のファイルパス）** を書き、次に **ALBのDNS名** を書いた ─ URLのパスと、ファイルシステムのパスと、ホスト名がすべて混ざっていた。`matcher` を `mather` とtypoして `validate` で捕まった。ALB本体・listener・TGの役割を「ALBが判断、TGが送信、listenerが接続可否」と逆に理解していた。

**腑に落ちた瞬間**
なぜヘルスチェックがTGにあるのか ─ **healthy/unhealthy は「EC2の属性」ではなく「EC2とTGの組み合わせの属性」だから**。同じ1台が `/` を叩くTGでは healthy、`/api/health` を叩くTGでは unhealthy になり得る。だから「このEC2は健康か」という問いは成立せず、「このEC2はこのTGのメンバーとして健康か」しか意味を持たない。個体は使い捨てで設定を持たないのだから、設定は入れ物側が持つ（第10回の Cattle, not Pets の一貫）。
そして `path = "/"` の意味 ─ ブラウザが送るのは `GET /` であり、`/var/www/html` は **Apacheだけが知っている翻訳ルール（DocumentRoot）**。Webサーバーの仕事の本質は「URLのパス → ディスク上のファイル」の翻訳であって、外から来る人は翻訳前の言葉しか話さない。
最後に、既定値と同じ値を明示しても plan は **`No changes`**。Terraformが比較しているのは「コードに書いてあるか」ではなく「あるべき状態と実際の状態」だから。**つまり明示はAWSのためではなく人間のためにやっている** ─ `health_check` が無いコードを読んだ人は、「何も考えなかった」のか「検討して妥当と判断した」のかを区別できない。

**面接で使える一言**
「ターゲットグループのヘルスチェックを既定任せにせず明示しました。値は既定と同じ30秒×2回ですが、コードに書くことで『最大60秒の断を許容する』という判断を記録に残せます。パスの選択は『何をもってアプリが生きていると見なすか』の設計判断で、DBまで確認する深いヘルスチェックにすると共有リソースの一時的な異常で全台が同時にunhealthyになり自滅します。だからヘルスチェックは『そのインスタンスを再起動すれば直る問題』だけを検知するように選び、依存先の異常はCloudWatchのアラームで見る、と役割を分けるべきだと考えています。」

**🔑 深掘り用キーワード**

## 第12回：RDS 導入 〜3層の完成と、パスワードを誰も知らない設計〜

**この回のテーマ**

**面接で使える一言**

**🔑 深掘り用キーワード**

## 第13回：積み残しの片付けとREADME整備 〜暗黙の既定を明示に変える〜
📅 2026-08-12

**この回のテーマ**
第12回で作ったRDSには、outputも `identifier` も運用設定も無かった。動きはするが、名前はAWSが自動生成した `terraform-20260810...` で、メンテナンスの時刻もAWSが勝手に決めている。**AWSに委ねていた決定を自分の手に取り戻す**のが前半。後半は、READMEがコードから3回分遅れていたので、食い違いを自分で洗い出して全面更新した（設計判断を10→14項目、既知の制約を6→8項目）。最後に apply して、**書いたばかりの手順を自分で実行して検証**した。

**つまずき**
`endpoint`（`host:3306`）と `address`（ホスト名のみ）の違いを知らず、`mysql -h` に何を渡すべきか判断できなかった。`identifier` に `db_name` 用の `replace()` をコピーして `portfolio_web`（アンダースコア）を渡した ─ **validateを素通りして、applyでAWSに弾かれる値**。`multi_az` を `multi-az` とkebabで書いた。閉じクォートを1つ落として**12個のエラー**を出した。`maintenance_window` を真偽値だと思い `false` と答えた。UTC→JST の変換を逆向きに計算した（10:00−9=1時としたが、正しくはUTCに+9）。「修正しました」と報告する前に `validate` を打たない癖を何度も指摘された。

**腑に落ちた瞬間**
「名前」が4つの層に分かれていること。**引数名（`multi_az`）はプロバイダーが決めた固定の綴りで、kebabかsnakeかという議論がそもそも成立しない**。自分で決められるのは、ラベル（snake_caseの慣習）・AWSに渡す値（DNS名になるのでkebab）・DB名（MySQLの制約でsnakeのみ）の3つだけ。`multi-az` は、この区別が無いまま「命名を揃えよう」という良い意図が事故になった例。

`maintenance_window` が「やるかどうか」ではなく「いつやるか」を指定する引数だったこと。**パッチ適用は断れない**。マネージドで手放したのは実施の有無で、手元に残っているのはタイミングだけ。だから引数が「いつ」を問う形をしている。しかもウィンドウは**開始してよい枠**であって完了保証ではないので、次の作業との間に余白が要る。バッファが買っているのは「衝突しない保証」ではなく「**何分の超過まで耐えられるか**」という量だった。

変更できるかを決めるのはTerraformではなく**AWSのAPI**だということ。`identifier` はrename APIがあるので `~ update in-place`（ただしエンドポイント名が変わるので無影響ではない）、`db_name` は変更APIが無いので `-/+ replacement`＝データが消える。直感とは逆に「箱の名前」は変えられて「中身の名前」は変えられない。見分け方はRegistryの **`Forces new resource`** の注記。

そして**ドキュメントには `terraform validate` が無い**こと。READMEに書いた手順を自分で実行したら、mysqlのプロンプトにPowerShellのコマンドを打ち込んでいた ─ ローカル→SSM→mysql の3階層から抜ける手順を、書いた本人が書き忘れていたから。**手順書は実行して初めて検証される**。

**面接で使える一言**
「RDS の `identifier` と、メンテナンス／バックアップのウィンドウを明示しています。書かなければ AWS が名前を自動生成し、実行時刻も勝手に選びます。動作は同じですが、コンソールの一覧・CloudWatch のメトリクス・請求の内訳で、どの DB か識別できなくなる。**決定の主体をコード側に取り戻す**という意図です。ウィンドウについては、それが『開始してよい枠』であって完了保証ではない点を踏まえ、マイナーバージョン更新の所要時間から逆算して30分のバッファを取りました。『余白を取った』ではなく『**何分の超過まで耐えられるか**』という量で設計しています。」

**🔑 深掘り用キーワード**

## ⑫ 第10回で増えたネタ ─ ASG・可用性・運用の境界

### Auto Scaling の構造
- [ ] **ASGが起動したEC2はTerraformの管理外** ｜芯：Terraformが作るのは「ASGという箱」まで。EC2はASGが実行時に起動するのでstateに載らずplanにも出ない。第9回27リソース→第10回も27（`aws_instance`と`target_group_attachment`が消え、`launch_template`と`asg`が増えた＝数は同じで中身が入れ替わった）。`describe-scaling-activities` の Cause に「Terraformの仕事の終わり」と「AWSの仕事の始まり」が2秒差で記録されている。
  💬「planの数は27＋ASGとテンプレート、EC2がAZまたぎで2台だから28？」
- [ ] **instance_id を output できなくなる ─ Cattle, not Pets** ｜芯：`aws_autoscaling_group` はインスタンスIDを属性に持たない（`terraform providers schema -json` で確認可）。台数が動的に変わるものをapply時点の静的な値に固定できないため。個体はNameタグで検索する。ASG構成では復旧手段は「入れ替え」であり、シェルアクセスは原因調査に限られる。実際にIPが `10.0.1.101 → 10.0.1.43` と変わり「直したのではなく捨てて建てた」ことが見えた。
  💬「outputのinstance idはどうやって抜き出すの？SSM接続がある以上いりますよね？」「異常時の対応ができない」
- [ ] **ALBとASGの結合点は `target_group_arns` の1行だけ** ｜芯：ALBはASGの存在を知らない。ASGが一方的にターゲットグループへ登録/解除する。だから台数が2→3→1と変わってもALB側のコードは不変＝疎結合。第9回は `aws_lb_target_group_attachment` で**人間が静的に**登録していた。
  💬「ASGとALBの関係性、通信の流れを教えて」
- [ ] **desired / min / max の役割分担** ｜芯：`desired_capacity`＝常に維持しようとする台数（**自己修復のエンジンはこれ**）、`min_size`＝床（スケーリングポリシーや手動操作でも下回れない保険）、`max_size`＝天井。min=desired=max=2 は「増減しない固定2台ASG」で、スケーリングポリシーを入れるなら max に余裕が要る。
  💬「minは今日でも意味がある、とは？スケーリングポリシーがないと意味ないのでは？」
- [ ] **SGはASGでなくlaunch_templateに付く** ｜芯：SGはENIに付く属性なので「EC2の設計図」側に書く。ASGは台数と配置を決める箱であってEC2の中身を決めない。`vpc_security_group_ids` / `image_id` / `instance_type` / `user_data` / `iam_instance_profile` は全部テンプレート側。
  💬「なぜSGはASGにつかないの？」「instance_typeは同じ引数でいける、amiでもいける？」

### 可用性とヘルスチェック
- [ ] **`health_check_type` は「壊れた」の定義を決める** ｜芯：既定 `"EC2"` はインスタンスのステータスチェック（OSの死活）のみ。httpdだけ死んだEC2は**健全と判定される**。`"ELB"` にするとターゲットグループのHTTPヘルスチェック結果も見るので、アプリ層の障害で入れ替わる。ALBを前段に置くなら実質必須。証拠は Cause の `ELB system health check failure`。
- [ ] **検知は瞬時ではない ─ 可用性は「影響時間の最小化」** ｜芯：ALBのヘルスチェック既定は interval 30秒 × unhealthy threshold 2回＝**最大60秒**は死んだEC2に振り分け続ける。この間は502が返る（503は健全ターゲット0のとき）。縮めるとアプリ負荷増＋誤検知のトレードオフ。障害ゼロは作れない。
  💬「httpd停止直後は正常に見えると思ったが、半分エラーになった」
- [ ] **ALBは切り離すだけ、殺すのはASG ─ 2段階ある** ｜芯：ALBが unhealthy にしても、そのEC2は普通に `running` のまま生き続ける（客を通さないだけ）。終了させるのはASGの仕事で別タイミング。さらに `running → shutting-down → terminated` は数分かかる。`--filters "Name=instance-state-name,Values=running"` で絞っていると「消えた」ように見えるが実際は状態が変わっただけ。
  💬「動かなくなったEC2は終了させるのでは？ずっとrunningで出ます」「SSMが繋いだままだとセッションは切れないの？」
- [ ] **ASG配下でプライベートサブネットを使う理由** ｜芯：ALB→EC2は同一VPCなので**localルート**で成立し、public/privateは無関係＝publicでも「動く」。privateにするのは経路そのものを断つため。publicに置くとパブリックIPが付き、IGWへの経路を持ち、**第8回で作ったVPCエンドポイントの存在意義が消え**、守りがSG1枚に減る（多層防御の喪失）。
- [ ] **AZ分散はASGが自動で均す（AZRebalance）** ｜芯：`vpc_zone_identifier` に複数サブネットを渡すとASGがAZ間で台数を均等配分。2台なら1a/1cに1台ずつ。壊した1台の代替も同じAZに立った。

### 運用とTerraformの境界
- [ ] **Terraformは名詞、CLIは動詞** ｜芯：恒常的な「あるべき構成」はコード、その場限りの操作はCLI/コンソール。スタンバイ・再起動・起動停止はコードに書かない（書くと「常にその状態であるべき」の宣言になりdriftの原因）。
  💬「スタンバイはどこになんの引数でつけるの？」
- [ ] **スタンバイ ─ 調査したい1台を生かしたまま外す** ｜芯：ASGのカウントから一時的に外す運用操作。ALBのターゲットからも外れ、終了もされない。`--no-should-decrement-desired-capacity` なら代替が起動しサービスは2台継続、`--should-decrement-...` なら台数を減らす。ただしスタンバイ中も上限にカウントされるため `max_size` に余裕が無いと代替を launch できない。
- [ ] **suspended_processes と protect_from_scale_in の違い** ｜芯：前者は**ASGの機能そのもの**を止める（Launch/Terminate/HealthCheck/ReplaceUnhealthy/AZRebalance…）＝ASG全体に効くブレーカー。後者は**インスタンス単位**の札で「スケールインの終了対象に選ばないで」だけ＝ヘルスチェック置換や手動terminateは防げない。調査用途にはどちらも過不足があり、スタンバイが第一選択。
  💬「suspended_processesとprotect_from_scale_inの違いは？」
- [ ] **CloudWatchで足りる範囲・足りない範囲** ｜芯：ログを個体の外に出しておけば個体が消えても残る＝第一手。限界は「**事前に出すと決めていないものは後から取りに行けない**」（メモリ、プロセス一覧、ディスクの中身、tcpdump）。だから現物確保（スタンバイ）の手段も要る。
  💬「CloudWatchで異常終了のログを出せば、インスタンスを残さなくてよいのでは？」
- [ ] **読むのは自由、書くのはTerraformだけ** ｜芯：Terraformで構築しても**調査はコンソール/CLIで行うのが正しい**。stateは「最後にapplyした時点のスナップショット」で現在の観測データを持たないため（ターゲットのhealthyもhttpdの生死もstateに無い。ASG配下のEC2に至っては存在すらしない）。ただし**構成変更だけはコンソールでやらない**＝drift。読み取り⭕/運用操作⭕/構成変更❌ の3分類。
  💬「Terraformで構築しても調査はコンソールで行うことが多いという事？」

### DNS ─ 権威とリゾルバ
- [ ] **名前解決するのは「通信を始めたい側」** ｜芯：軸はインバウンド/アウトバウンドではなく**問い合わせる人がどこにいるか**。VPC内のEC2が引くならVPCリゾルバ（`.2`アドレス）、自宅PCがALBのDNS名を引くならISPのリゾルバ。**インバウンドのときVPCリゾルバは一切登場しない**。
  💬「アウトバウンドはVPCリゾルバが名前解決していた。ではインバウンドのパブリックIPは誰が名前解決しているの？」
- [ ] **権威サーバとフルサービスリゾルバ** ｜芯：権威＝答えを持っている人（`*.elb.amazonaws.com` はAWS/Route 53が権威）、フルサービスリゾルバ＝答えを探しに行く代理人（ISPのDNS、8.8.8.8、**VPCリゾルバもこちら**）。ルート→.com→amazonaws.com と辿る。
- [ ] **split-horizon DNS ＝ private_dns_enabled の正体** ｜芯：同じ `ssm.ap-northeast-1.amazonaws.com` でも、VPC内から引けばエンドポイントのプライベートIP、外から引けばパブリックIP。「誰が聞くかで答えが変わる」仕組み。第8回の伏線回収。
- [ ] **ALBをIPで参照してはいけない理由** ｜芯：ALBのIPはAWSが裏で付け替える（TTL 60秒）。だからoutputは `dns_name`。固定IPが要件なら NLB を選ぶ、という設計判断につながる。

### AWS CLI / API の読み方
- [ ] **`--filters` の `Name=` は2つの意味を持つ** ｜芯：`Name=tag:Name,Values=test_ec2` の最初の `Name=` は「フィルタ名の指定」という決まり文句、`tag:Name` がタグのキー名。`instance-state-name` はAWS定義済みのフィルタ名。
  💬「`Name=instance-state-name` は要るの？ tag:Nameは自分で付けた名前だから分かる」
- [ ] **terminateしたEC2は消えず `terminated` として約1時間残る** ｜芯：`describe-instances` は「状態を問わず全部」返す。タグだけで絞ると過去の残骸が混ざり、どれが生きているか分からない。「削除」ではなく「状態遷移」で捉えるのがAWSの流儀。
- [ ] **`Reservations[].Instances[]` の2階建て** ｜芯：Reservation＝1回の起動リクエスト単位のまとまり。「3台まとめて起動」なら1 Reservationに3 Instances。EC2最初期からの歴史的構造。`[]` は配列を平らに開く記号（JMESPath）。
  💬「`Reservations[].Instances[]` とは何？」
- [ ] **`--query` は自分で選ぶ射影 ─ 出ないのは指定していないから** ｜芯：`.{ID:InstanceId,AZ:Placement.AvailabilityZone}` のように `{}` でキー名を付けると `--output table` にヘッダが付く。AZが `Placement` の下にあるのは配置情報（AZ・配置グループ・テナンシー）がそこにまとまっているため。
  💬「これではどちらのAZにあるEC2か分からなくないですか？」
- [ ] **`describe-scaling-activities` の Cause が一次ソース** ｜芯：ASGが「いつ・何を・なぜ」やったかの行動ログ。`Description`（何をしたか）と `Cause`（なぜか）は別フィールドで、証拠になるのは `Cause`。「新しいEC2が立った」だけでは自己修復の証明にならない。
- [ ] **1アクティビティ＝インスタンス1台に対する操作1回** ｜芯：apply（desired 0→2）は判断1回でも起動2台なので**2行**になる。自己修復も `Terminating` と `Launching` の**別々の2行**＝「置き換え」という単一操作は存在しない。**ASGの作成自体は行にならず、`Cause` の文章の中に原因として残る**（行になるのはインスタンスが動いたときだけ）。`--max-items` は取得上限であって絞り込みではない。
  💬「なぜ4項目出てきたの？」
- [ ] **ログの寿命はサービスごとに違う ─ リソースに紐づくログはリソースと死ぬ** ｜芯：ASGアクティビティはASG削除で消滅（残っても6週間）、terminatedインスタンス情報は約1時間、CloudTrailは90日、CloudWatch Logsは保持期間次第。**destroy運用だと毎回リセットされる**ので、証拠にしたいログはその場で手元に落とす。
  💬「今後applyするたびに取れる結果は増えていく？」

- [ ] **API名をケバブケースに崩すだけでCLIになる** ｜芯：`DescribeScalingActivities` → `aws autoscaling describe-scaling-activities`。動詞規則は describe-*(詳細)/list-*(一覧)/get-*(単一)/create・delete・update。**引っかかるのはサービス名の方**（ELBは`elbv2`、Auto Scalingは`autoscaling`）。

### 調査とログの居場所 ─ CloudTrail
- [ ] **CloudTrailはリソースに紐づかない ─ APIの玄関に立っている** ｜芯：コンソールもCLIもTerraformも、すべてAWS APIへのHTTPSリクエスト（第9回「AWS APIは基本HTTPS443」の回収）。CloudTrailはEC2の中にもASGの中にもおらず、**手前の共通の通り道**で全部を記録する。だから横断的に見える。`terraform apply` の全APIも当然残る。
  💬「EC2などに紐づいていないのに確認できるの？」
- [ ] **ログの3層構造** ｜芯：①**APIの層**＝誰がEC2を終了したか（CloudTrail・横断・90日）②**サービス内部の判断**＝ASGがなぜ終了させたか（ASGアクティビティ・内蔵・消える）③**OS/アプリの中**＝httpdがなぜ落ちたか（インスタンス内・**消滅する**）。CloudTrailは一番外側しか見ないので、APIを経由しない出来事（プロセス死亡・ディスク溢れ）は一切記録されない。→ CloudWatch Logsが要る理由。
  💬「terminatingは記録上ASGに残っているだけで、それ以上のログは何も残らない？」
- [ ] **イベント履歴（既定ON）と証跡（自分で作る）は別物** ｜芯：**イベント履歴**＝全アカウントで常時ON・止められない・管理イベントのみ・そのリージョン・90日・無料。**証跡(Trail)**＝作らないと存在しない・S3配信で無期限・データイベント可・マルチリージョン集約可。`lookup-events` が読むのは**イベント履歴**なので、証跡ゼロでも権限さえあれば返る。
  💬「CloudTrailを立ち上げていないのに記録されている？」
- [ ] **証跡を作ると「見に行く場所」が「使えるデータ」になる** ｜芯：①データイベント（**tfstateバケットを誰が読んだか**はこれでしか取れない）②CloudWatch Logs連携で**能動的な検知・通知**（rootログイン、SGに0.0.0.0/0追加）③AthenaでSQL検索 ④監査要件（90日では多くの基準を満たさない）⑤ログ検証＋オブジェクトロックで保全。**受動→能動**への転換。
  💬「自分でCloudTrailを作ったときと具体的に何が異なるの？」
- [ ] **「既定でONか」の判断手順** ｜芯：①**何も作っていない状態でコンソールを開いてみる**（中身があれば既定ON）②`describe-*`/`list-*` で「今あるもの」を確認（`describe-trails` が空なのにイベント履歴は見える＝独立の証拠）③**料金ページを見る＝無料のものは既定で有効なことが多い**。逆に課金対象（データイベント/Interfaceエンドポイント/NAT）は必ず自分で作るもの。**AWSは黙って課金を始めない**。
  💬「規定でとは、どのように判断する？」
- [ ] **管理イベントとデータイベント／証跡1本目は実質無料** ｜芯：管理イベント（作成・削除・設定変更）は既定ON・無料、データイベント（S3のGET/PUT、Lambda実行）は既定OFF・有料＝**量が桁違いだから**。「何を記録するか」もコスト設計。なお管理イベントの証跡1本目はAWSが1コピー分を負担するのでS3保管料のみ＝実務では「作らない理由がない」。

### ポートとプロトコル ─ 層の分離（本人が「非常に苦手」と申告した領域）
- [ ] **「443だからHTTPS」は因果が逆** ｜芯：ポート番号は16ビットの数値でしかなく、中身の言語を決めない。443で独自プロトコルも8443でHTTPSも可能。判断は必ず**①宛先は何者か → ②それは何を喋るか → ③ならば何番か**の順で、逆から辿ると必ず間違える。今回443がHTTPSなのは「443だから」ではなく**待ち受けているのがAWS APIだから**。
  💬「ポート443はHTTPSなの？」「VPC内の443の通信はHTTPSになるという理解であっている？」
- [ ] **層は"変わる"のではなく入れ子（カプセル化）** ｜芯：L3（宛先IP＋プロトコル番号6=TCP）／L4（TCPヘッダの送信元・宛先ポート）／L7（中身）が**1つのパケットに同時に存在**する。TCPがHTTPに化けるのではなく、封筒の中に手紙が入っている。80と443の区別がつくのは**L4から**。
- [ ] **解釈するのはポートではなくプロセス** ｜芯：OSはポート番号を見て「どのプロセスに渡すか」を仕分けるだけで、中身の意味は見ていない。443に届いたデータをsshdに渡せばSSHとして解釈される。**誰も「これはHTTPSだ」と宣言していない**。
- [ ] **層を分ける4つの利点** ｜芯：①**多重化**（1つのIPで複数サービス。無ければ1台1サービス）②**再利用**（「確実に届ける」をTCPが一度だけ解決し、HTTPもSSHも再送や順序整列を自前実装していない）③**独立した進化**（HTTP/2化でルーター交換は不要、TCPの改良は全アプリが自動で享受）④**中継の自由度**（下位層だけ見れば運べる→NLBは何でも運べ、ALBはHTTPのみ）。
  💬「アプリケーション層になるとsshやhttp,httpsに変わるのはなぜ、どういう利点があるの？」
- [ ] **ウェルノウンポートの実利＝事前交渉の省略** ｜芯：慣習が無いと「HTTPSは何番ですか」を聞く手段自体が無い（鶏と卵）。IANAが0〜1023を管理。**合意であって強制ではない**ので8443でも動くが、その場合は `:8443` と明示が要る。
- [ ] **ポートは"代理指標"であって判定ではない** ｜芯：中身の確認には重いパースが要るが、番号なら16ビットの比較1回で済む。SGは「443だからたぶんHTTPS」と**推測**しているだけで保証はない（443でSSHを流せば通してしまう）。だから**安くて雑な網（SG＝L3/L4）と高価で精密な網（ALB＝L7振り分け／WAF＝中身の検査）を重ねる**＝多層防御の一形態。
- [ ] **比喩：IP=住所／ポート=部屋番号／TCP・UDP=配送方法／L7=手紙の言語／SG=封を開けない警備員** ｜芯：警備員は「443号室宛だから英語の手紙だろう」と推測して通しているだけ。封を開ける係（WAF・ALB）は別に雇う必要がある。1つの住所に複数の部屋があるから1台で複数サービスが同居できる。
  💬「IPが住所ならポートは何にあたる？」
- [ ] **同じ `protocol` 引数でも指定する世界が違う（コードに露出している）** ｜芯：SGは `protocol = "tcp"`（L4）、ALBリスナーは `port = "80"` ＋ `protocol = "HTTP"`（L4＋L7）。**port と protocol が別引数であること自体が「80番＝HTTPは固定ではない」の証明**。ALBが中身を読むのは検査のためでなく**振り分けという仕事のため**で、400 Bad Request は副産物。**ALBは防御装置ではない**（正しいHTTPに載った攻撃は素通し＝WAFの仕事）。
  💬「ALBは中身まで読んでHTTPか確認している、SGはしていないであっている？」

### TLS と AWS API の通信
- [ ] **経路（L3）とプロトコル（L7）は独立している** ｜芯：VPCエンドポイント経由でインターネットを介さなくても、通信はHTTPS。エンドポイントは**宛先IPをプライベートに変えるだけ**で中身のプロトコルには関与しない。「社内の内線に切り替えても日本語で話すのは変わらない」。だからエンドポイント側は443で受ける必要がある（第8回の `endpoint_sg` の正体）。
  💬「エンドポイント経由でインターネットを介さない通信なのに、なぜHTTPSが出てくるの？」
- [ ] **`private_dns_enabled` は証明書検証を成立させるためでもある** ｜芯：TLS証明書は**ホスト名に対して**発行される。名前を `ssm.ap-northeast-1.amazonaws.com` のまま保ち、解決されるIPだけをプライベートに差し替えるから検証が通る。IPを直接叩くと証明書と一致せず失敗する。「経路をprivateにする」だけの機能ではない。
- [ ] **TLSの主目的は暗号化よりサーバー認証** ｜芯：TLSが提供するのは暗号化・完全性・**サーバー認証**の3つ。暗号化だけでは「偽サーバーと安全に会話する」だけで意味がない。SSMエージェントは**IAMの一時認証情報で署名したリクエスト**を送るため、偽サーバーに繋がれば認証情報が渡ってしまう。証明書検証がそれを防いでいる。
- [ ] **コントロールプレーンとデータプレーン** ｜芯：「AWSへの指示」（EC2を起動しろ等）は全サービス一律 **HTTPS 443**＝例外を作る方が複雑だから。「サービスが本来喋る言葉」は RDS 3306 / Redis 6379 / NFS 2049 など固有。**CloudTrailが記録するのは前者だけ**。
- [ ] **なぜVPC内でも暗号化するのか（3つの理由の重み）** ｜芯：①AWS APIが一律TLSで統一されている（**実務上の主因**）②サーバー認証が必要（**技術的な本質**）③ネットワーク上の位置で信頼を決めない＝ゼロトラスト（**設計思想**）。③は「privateサブネットで経路を断つ」「SGを重ねる」と同じ一貫した態度の延長。

### セキュリティグループの書き方 ─ 迷わないための手順
- [ ] **4ステップで機械的に決まる** ｜芯：①**接続を開始するのはどちらか**を決める（**SGは受ける側に書く**）②受ける側のサービスが決まればポートとプロトコルは決まる（**調べる対象であって考える対象ではない**）③通信元がSGを持つAWSリソースなら `security_groups`、外部・不特定なら `cidr_blocks`、AWSサービス群なら `prefix_list_ids` ④**outboundは基本書かない**（ステートフルなので戻りは自動で通る）。迷ったら必ず①に戻る。
  💬「SGに何を書いたらいいのか、いつも迷います」
- [ ] **SGの protocol 欄はL7ではない＝だからポートが要る** ｜芯：書けるのは `tcp` / `udp` / `icmp`（L4）だけで、HTTP・SSH・MySQLは書けないし見えない。もし「tcpを許可」しか書けなければ httpd も sshd も MySQL も**全部まとめて通ってしまう**。プロトコルだけでは区別できないからポート番号が必要になる。
  💬「大事なのはプロトコルという事ですね、ではポートは何のためにある？プロトコルだけでもいけそう」
- [ ] **SSM接続にEC2のinboundルールは要らない** ｜芯：ステップ①で「接続を開始するのはEC2側（アウトバウンド）」と分かるため。実際 `ec2_sg` のinboundはALBからの80番のみで、SSM用のルールは1行もない。「サーバーに入る」という語感に引きずられると必ず間違える。
- [ ] **Gatewayエンドポイントには書くものが無い** ｜芯：ENIもSGも持たない（ルーティングで経路を曲げる仕組み）。`subnet_ids` / `security_group_ids` を要求するのは Interface エンドポイントだけ。

## ⑬ 第11回で増えたネタ ─ ヘルスチェック・URLとファイルパス・明示の価値

### ヘルスチェックはなぜTGにあるのか
- [ ] **healthy/unhealthy は「EC2の属性」ではなく「EC2とTGの組み合わせの属性」** ｜芯：同じ1台が、`/` を叩くTGでは healthy、`/api/health` を叩くTGでは unhealthy になり得る。だから「このEC2は健康か？」という問いは成立せず、「**このEC2はこのTGのメンバーとして健康か？**」しか意味を持たない。判定の仕様も結果も、置き場所はTGしかない。ALB本体に置けば行き先ごとに違うパスを叩けず、EC2側に置けば使い捨ての個体に設定を持たせることになる（第10回 Cattle, not Pets の一貫）。
  💬「いまさらですが、なぜヘルスチェックはtgにあるの？」「alb側の設定ではないのですか？」
- [ ] **設定を書く場所と、実際にチェックする人は別** ｜芯：設定は全部TGの `health_check` ブロック1か所。ALBは**HTTPリクエストを実際に送る実行者**、TGは**仕様と判定結果を持つ場所**、ASGは `health_check_type = "ELB"` の1行で**その結果を読んで置き換える人**。1つの状態（healthy か否か）を3者が違う立場で扱っている。第10回の「ALBは切り離すだけ・殺すのはASG」の時間差の正体がこれ。
  💬「トラフィックを流すかどうかの設定はALBにあるなら、ASGのhealthy_thresholdとはなに？」
- [ ] **TGの状態にはEC2に無い概念がある** ｜芯：`aws ec2 describe-instance-status`（running / 2/2 checks passed）と `aws elbv2 describe-target-health`（healthy / unhealthy / **initial** / **draining**）は別物。`initial`＝登録直後でまだトラフィックが流れない、`draining`＝新規は流さないが処理中のリクエストは終わるまで待つ。EC2から見れば単にrunningのままで、**同じ1台を違う立場が違う言葉で語っている**。
  💬「つまり、EC2のステータス状況をまとめているのもTGということ？」
- [ ] **healthy_threshold は「検知」ではなく「投入」の速度** ｜芯：失敗側の閾値＝障害の検知が速いか遅いか（＝断の長さ）、成功側の閾値＝新規/復帰インスタンスが実際にトラフィックを受け始めるまでの時間。ASGが起動した直後のEC2は running でも `dnf install httpd` の途中で、そこに流せば502を返す。だから連続成功を求める。**大きくすると安全だがスケールアウトの反応が鈍る**。
  💬「healthy_thresholdに関して、連続で成功しないとトラフィックを流さないという事ですか？」
- [ ] **ヘルスチェックの「深さ」とカスケード障害** ｜芯：浅い（静的ファイル）＝Apacheが生きていればhealthy＝アプリ死亡を見逃す。深い（DBにSELECTして200）＝依存先まで保証できるが、**DBが一瞬詰まっただけで全台が同時にunhealthyになりASGが全台を置き換え始める**＝アプリは無事なのに全滅。定石は「**アプリ自身が応答できるかはヘルスチェック、依存先の異常はCloudWatchアラーム**」の役割分担。ヘルスチェックの結果は**インスタンスを殺す引き金**なので、殺して直る問題だけを見るべき。
  💬「これを具体的なパスを指定するときはどんな時？」
- [ ] **実務で `/` を使わない3つの理由** ｜芯：①トップページは重い（DB問い合わせ・画面描画）のに30秒ごと×全台×ALBノード数だけ叩かれる→軽い `/health` を用意②パスでTGが分かれていると `/api/*` 用TGに `/` を投げても404③`/` が認証で302にリダイレクトされる（この場合は `matcher = "200,302"` に広げる手もある）。
- [ ] **EC2ステータスチェックは無設定・無料で常時動いている** ｜芯：コンソールの「2/2 のチェックに合格しました」がそれ。システム（AWS側の物理ホスト・電源・ネットワーク）とインスタンス（OSが起動したか・到達可能か）の2つ。**ASGは自分でチェックしておらず、EC2が常に出している結果を読んでいるだけ**だから設定項目が無い。`health_check_type` の既定が `"EC2"` なのは、**ASGはLBとセットとは限らない**（バッチの群れなど）ため。だから第10回で「既定のままではhttpdの死亡を検知できない」＝**OSは生きているので2/2合格のまま**。
  💬「とくに設定していないが、勝手にEC2健康状態を取得しにいくの？」

### URLのパスとファイルシステムのパス（Webサーバーの基礎）
- [ ] **`path` はURLのパスであって、サーバー上のファイルの場所ではない** ｜芯：URLは `スキーム :// ホスト名 / パス` の3部構成で、`path` に入るのはホスト名より後ろだけ。ALBはもう宛先（ターゲットのprivate IP）を知っているので、残る空欄は「**その相手に何を注文するか**」だけ。ホスト名を書くと外に出て自分に戻ることになるし、そもそも `/` で始まらないのでAPIに拒否される。
  💬「EC2がプライベート環境にありパブリックにあるのはALBですよね、ではこのパスになにを書けばいいのかわからない」
- [ ] **Webサーバーの本質は「URLのパス → ディスク上のファイル」の翻訳** ｜芯：ブラウザが送るのは `GET /`、ファイルがあるのは `/var/www/html/index.html`。この2つを結んでいるのがApacheの **DocumentRoot（/var/www/html）＋ DirectoryIndex（index.html）** という設定。外から来る人は翻訳前の言葉しか話さず、翻訳後の言葉はApacheの中だけで使われる。DocumentRootを変えれば同じ `GET /` が別のファイルを返す。
  💬「なぜ"/"これで行けるの？Apache の中の事情とはなに？」
- [ ] **パスはネットワーク上の位置と無関係** ｜芯：`[PC] --GET /--> [ALB(public)] --GET /--> [EC2(private):80]`。ヘルスチェックは後半の矢印だけをALBが定期的に投げているもの。第9回の比喩に足すと **IP=住所／ポート=部屋番号／パス=その部屋の人への注文**。住所がprivateでもpublicでも注文の内容は変わらない。
- [ ] **同じ「間違い」でも捕まる層が違う** ｜芯：`path = "/var/www/html/index.html"` は validate も plan も apply も通り、**稼働してから全台unhealthy→無限に置き換わり続ける**（Terraformが検出できない誤りの6例目）。`path = aws_lb.alb.dns_name` は型がstringなのでvalidate/planは通るが**applyでAWSがValidationError**。`mather` のtypoは**validateで即死**。どこで捕まるかは「誰がその値の意味を知っているか」で決まる。

### ALB三点セットの役割分担
- [ ] **判断=listener、宛先の集合=TG、実体=ALB本体** ｜芯：`aws_lb`＝DNS名を持ち各AZに足を出す**建物**、`aws_lb_listener`＝何番で待ち受け来たものをどう扱うか決める**受付**、`aws_lb_target_group`＝メンバー一覧と健康判定の仕様を持つ**名簿**。コードを見ると判断（`default_action`）が書いてあるのはlistenerだけで、**TGには「送る」という動詞が1つも無い**。
  💬「ALBがトラフィックを分けるか判断して、それを実際に送るのがTG、繋げるかどうかがlistenerであっている？」
- [ ] **listenerはforward以外もできる** ｜芯：`type = "fixed_response"` ならTGを一切見ずに固定レスポンス（メンテナンス中の503）、`type = "redirect"` ならHTTPS(443)へ飛ばす。**「問答無用で繋げなくする」もlistenerの機能**。だから判断の主体はlistenerだと分かる。
- [ ] **`matcher` はレスポンスのステータスコード** ｜芯：リクエストではなく、EC2が返してきた応答が成功か。`"200"` / `"200-299"` / `"200,302"` のように範囲・複数指定が可能。「`/` が認証で302を返す」ならパスを変えるかmatcherを広げるかの2択。

### 既定値と明示 ─ コードは誰のために書くのか
- [ ] **既定値と同じ値を明示しても plan は `No changes`** ｜芯：Terraformが比較しているのは「コードに書いてあるか」ではなく「**あるべき状態と実際の状態**」。ヘルスチェックの間隔は書く前からAWS側で30秒だった。**インフラを1ミリも変えずにコードだけを変えた**ことになる。値を変えていれば `1 to change`（TGはin-place更新可）、`name` のようにAWSが再作成でしか実現できない属性なら `1 to destroy, 1 to add`。
- [ ] **明示はAWSのためではなく人間のため** ｜芯：`health_check` が無いコードを読んだ人は、「この人は何も考えなかった」のか「30秒×2回を検討して妥当と判断した」のかを**区別できない**。コードは実行される指示であると同時に**設計判断の記録**であり、ポートフォリオではむしろ後者が読まれる。面接で「間隔は何秒ですか」に「書いてないです、既定です」と答えるのとの差。
- [ ] **ドキュメントが読めない時の最終手段は `terraform providers schema -json`** ｜芯：プロバイダー本体が持っている定義そのものなので、ドキュメントより正確。`> schema.json` はコマンドを実行したディレクトリに出るが数MBあり再生成可能なのでgitに入れない（第6回の `.terraform/` と同じ判断軸）。なおRegistryのページ名は `aws_` が落ちて `lb_target_group` になっている。
  💬「例がなくて何を書けばいいかわからない、引数自体はあります」「schema.jsonはどこにある？」
- [ ] **`terraform fmt` は既定でカレントディレクトリしか見ない** ｜芯：サブディレクトリの `.tf` は素通りするので、モジュール構成なら `-recursive` が要る。「参照の境界はモジュール、整形の境界はディレクトリ」。
  💬「-recursiveとはなに？」

## ⑭ 第12回で増えたネタ ─ RDS・マネージド・認証情報・IAM Condition

### マネージドサービスとは何か
- [ ] **責任の分界点が上にせり上がること** ｜芯：EC2では「データ／スキーマ／DBエンジン／OS・パッチ」が全部ユーザー責任で、AWSは仮想化とハードだけ。RDSでは「DBエンジン／OS・パッチ」がAWS側に移る。**証拠は第10回の `dnf install -y httpd` を自分で書いたこと** ─ ミドルウェアの導入がユーザーの仕事なのがIaaS。RDSではMySQLのインストールもパッチ当ても書かない。
  💬「マネージドサービスとはユーザで管理するのではなく、AWSで管理するリソースであっている？」
- [ ] **RDSのメンテナンスとは何か／EC2でも起こるのか** ｜芯：①DBエンジンのマイナー更新②OSのパッチ③基盤ハードの交換。**③はEC2にも起こる**（「スケジュールされたイベント」で再起動・停止・リタイア通知）。違うのは①②で、EC2では誰も当ててくれないので自分で `dnf update` か Patch Manager を組む必要がある。**今のEC2は誰もパッチを当てていない状態**。
  💬「EC2はマネージドサービスではないから、RDSのメンテナンスとは何ですか？EC2などには起こりえないの？」
- [ ] **マネージドでは運用が「名詞」としてコードに現れる** ｜芯：`maintenance_window` / `backup_window` / `auto_minor_version_upgrade` / `backup_retention_period` ─ **バックアップもパッチ適用も「設定」として宣言できる**。EC2にこんな引数は無い。第10回の「Terraformは名詞・CLIは動詞」の続きで、**運用作業がAWS側に移った結果、宣言的な設定として表に出てきた**のがマネージドの正体。
- [ ] **ステートフルなものは家畜にできない** ｜芯：EC2は壊れたら捨てて作り直せる（Cattle）が、RDSは**中にデータがあるから捨てられない**（Pets）。**捨てられないものだけが丁寧な世話を必要とし、その世話は難しく失敗が致命的だから、AWSに金を払う価値がある**。逆にステートレスなWebサーバーをマネージドにする動機は薄い。
- [ ] **DBサブネットグループは「配置」ではなく「配置可能範囲」** ｜芯：登録した全AZに置かれるわけではない（実機で1a/1cを登録し**1cにしか存在しなかった**）。AWS側の都合でAZを移ることがあるマネージドサービスなので、**移動先を先に許可**させる。ALBが「全AZに実体を置く」のとは意味が違う。**Multi-AZは後から有効化できるが、1AZしか登録していなければできない**＝今日の1行が将来の選択肢を決める。
- [ ] **RDSが作るものはstateに出ない** ｜芯：`manage_master_user_password = true` と書いてもplanに `aws_secretsmanager_secret` は出ない（30 to add に含まれない）。**RDSが自分で作るから**。第10回の「ASGという箱までがTerraform、EC2はAWSが作る」と同じ構図。管理を委ねた分だけTerraformの視界から消え、destroyでは持ち主が片付ける。シークレット名の **`rds!` プレフィックスが「RDS所有」の印**（ユーザーは読めるが削除・変更不可）。

### 「ステートフル」という同音異義語（今日一番の混乱ポイント）
- [ ] **SGのステートフルと、リソースのステートフルは無関係** ｜芯：**SGがステートフル**＝行きの通信を記憶して戻りを自動で通す（対義語＝**ネットワークACL**、戻り用ルールも自分で書く）。**RDSがステートフル**＝データを保持し捨てると失われる（対義語＝Webサーバー）。たまたま同じ英単語なだけ。
  💬「RDSもS3へバックアップを書くなら、ステートフルといえるのでは？」
- [ ] **SGの挙動はリソースの種類に一切依存しない** ｜芯：`EC2→SSMエンドポイント`（EC2のinbound不要）、`EC2→RDS`（EC2のinbound不要／RDSのinbound必要）、`RDS→S3`（RDSのinbound不要）─ **判断材料は常に「誰が接続を開始したか」だけ**。EC2が「ステートレス（＝捨てられる）」なのはASGで置き換えるための性質の話で、SGとは無関係。
  💬「ステートレスなEC2のSSM通信の時、インバウンドのSGは書かなかったが、ステートレスとフルで何か変わるの？」
- [ ] **「論理的に必要な許可」と「コードに書くもの」は別** ｜芯：EC2のoutbound 3306は**論理的には必要**だが、既定の全許可に含まれるので書かない。「不要だから書かない」ではない。**egressを最小権限に絞る設計に変えた瞬間、EC2側にoutbound 3306を明示する必要が生まれる**。
- [ ] **Terraformはegressの既定ルールを削除する** ｜芯：AWSはVPC内にSGを作ると allow-all egress を自動で付けるが、**Terraformはそれを削除する**（明示しない限り）。だから既存の `ec2_sg` にはわざわざ全許可のegressが5行書いてある。理由は「**コードに書いていないものは存在しない**」という宣言的ツールの一貫性 ─ AWSの親切を一度取り消して、コードを唯一の真実にしている。第11回の `health_check`（既定と同じでも書く）と同じ思想。
  💬「AWS側では書かないと全許可だが、terraformだと全拒否になるとか？」（本人正答）

### 認証情報を持たない設計
- [ ] **tfvars とは何か** ｜芯：`variables.tf` が**入力の口の宣言**（仮引数）、`terraform.tfvars` が**実際に渡す値**（実引数）。`terraform.tfvars` という名前なら自動で読まれる。**コード（共有する）と値（環境ごとに違う・秘密を含む）を分離する**のが目的で、だから `.gitignore` に `*.tfvars` が入っている。
  💬「tfvarsとはなんですか？」
- [ ] **`sensitive = true` ＋ tfvars では守れない ─ stateに平文で残る** ｜芯：`sensitive` は**画面表示を隠すだけ**で state は暗号化されない。tfvars はgitに入らないが、applyの結果は state に記録される。第6回で tfstate を gitignore した理由「秘密情報が平文で入る」がここで効く。**stateを読める人＝DBパスワードを読める人**。第7回で「tfstateバケットを誰が読んだかはCloudTrailのデータイベントでしか取れない」と気にした理由もこれ。
- [ ] **`manage_master_user_password = true` ＝ そもそも秘密を扱わない** ｜芯：RDSがパスワードを生成しSecrets Managerに保存、Terraformが受け取るのは**ARNだけ**。実機のstateには `master_user_secret`（ARN）と `password_wo = (write-only attribute)` しか無く、平文は1文字も無い。**人間の頭にも、ファイルにも、stateにも存在しない**。守るより「入れない」方が確実。
  💬「manage_master_user_passwordについて、どういう引数？なぜ必要なの？」
- [ ] **Secrets Manager と SSM Parameter Store の違い** ｜芯：両方とも秘密を保存できるが、**自動ローテーション**とRDS統合があるのはSecrets Manager（有料 約$0.40/月）。Parameter Store は standard が無料で汎用の設定値ストア。**「誰も知らないパスワードが定期的に勝手に変わる」状態を作れる**のが前者。人間が知っているパスワードは、いずれ手順書やSlackに貼られる。

### IAM ─ 最小権限のコツと Condition
- [ ] **権限は芋づる式に必要になる（マネージドの代償）** ｜芯：apply が3回止まった ─ ①`rds:CreateDBSubnetGroup` ②KMS（`storage_encrypted` と Secrets Manager の暗号化）③`secretsmanager:CreateSecret`。**AWS管理ポリシーは「そのサービスの操作」しかカバーしない**ので、サービス間連携が権限の穴になる。`manage_master_user_password` は「RDSが作る」ように見えて**あなたの権限で代理作成している**。
- [ ] **AWSは最初に失敗した1つでしか止まらない** ｜芯：だから「apply→エラー→権限追加」を繰り返すしかなく、**必要権限は静的解析では洗い出せない**。第7回の「机上で洗い出すより実績から絞る方が確実」の実体験。
- [ ] **最小権限は「後から絞る」** ｜芯：①広い管理ポリシーでまず動かす②CloudTrailで実際に呼ばれたAPIを収集③**IAM Access Analyzerでポリシーを自動生成**④絞って**全部テストし直す**。④を飛ばすと「半年後のdestroyで初めて権限不足に気づく」。今日 `secretsmanager:DeleteSecret` を先回りで入れたのがこれ。**作る権限だけ付けて片付けられなくなるのは頻出事故**。
- [ ] **絞る軸は Action / Resource / Condition の3つ** ｜芯：多くの人はActionしか絞らない。読み取り（`Describe*` `List*` `Get*`）は絞る優先度が低く、`Create*` `Delete*` `Put*` が事故になる。**Statementを分ける理由は Resource か Condition が違う時**（第7回のS3ポリシーが2つに分かれていたのと同じ）。
  💬「この最小権限のつけ方のコツ、およびconditionsについてもう少し詳しく教えて」
- [ ] **Conditionの構造は3階層** ｜芯：`"Condition": { "演算子": { "コンテキストキー": "値" } }`。コンテキストキーは**リクエストに付随する情報**（誰が・どこから・どうやって呼んだか）。演算子＝`StringEquals`/`StringLike`/`Bool`/`IpAddress`/`ArnEquals`/`Null`。よく使うキー＝`aws:MultiFactorAuthPresent`/`aws:SourceIp`/`aws:RequestedRegion`/`aws:ResourceTag/<key>`/`kms:ViaService`。
- [ ] **最大の落とし穴：キーが存在しない時は「拒否」** ｜芯：`kms:ViaService` は**AWSサービス経由の時だけ存在する**。Terraformが直接 `kms:ListAliases` を呼ぶ時は存在しないので、条件が判定できず Allow が成立しない。**「条件に合わない」だけでなく「判定できない」場合も拒否**。回避は `StringEqualsIfExists`（ただしキーが無ければ素通しなのでセキュリティは弱くなる）か、Statementを分ける。
  💬「"Condition"の部分でjsonの構文エラーになります」
- [ ] **実務で効くCondition 3つ** ｜芯：①**リージョン制限**（`aws:RequestedRegion` ＋ Deny で「知らないリージョンでEC2が動いていた」を構造的に防ぐ）②**MFA必須**（`aws:MultiFactorAuthPresent: false` ＋ Deny）③**ABAC**（`aws:ResourceTag/Owner` = `${aws:PrincipalTag/Team}` で「自分のチームのリソースだけ触れる」。**リソースが増えてもポリシーが増えない**のが利点で、`default_tags` で全リソースにタグを付けている構成と相性が良い）。**Deny + Condition が最強**＝明示的Denyは必ず勝つので、ガードレールはDenyで作る。
- [ ] **`Resource: "*"` が避けられない時はConditionで絞る** ｜芯：AWSマネージドキーのARNは事前に確定しない（アカウントごとに違い、まだ存在しないこともある）。権限を絞る手段はResourceだけではない。

### バージョンとEOL
- [ ] **IaCでバージョンを固定するとEOLに気づかず放置される** ｜芯：コードに書いた瞬間それは凍結され、**動き続けているものは誰も見に行かない**。実際 `5.7`（サポート切れ）→ `8.0` に直そうとしたら**8.0も2026-07-31に標準サポート終了**していて、Extended Support（有料）が自動で始まる状態だった。`auto_minor_version_upgrade` はマイナー更新しか救わない。**メジャーバージョンのEOLは人間が能動的に管理する対象**であり、IaCは守ってくれない。
  💬「MySQLのバージョン8.0は延長サポートまで終了しているとありますが、いいのですか？」（**本人が自分で調べてClaudeの提案を訂正した**）
- [ ] **使えるバージョンはAWSに直接聞く** ｜芯：`aws rds describe-db-engine-versions --engine mysql --query "DBEngineVersions[].EngineVersion"` で**そのリージョンで今作れるものだけ**が返る。存在しない `9.7` を書く事故も防げる。第10回の「カタログを眺めず実データで確認する」の応用。`engine_version = "8.4"` とだけ書けばパッチ版（実際は8.4.9）はAWSが選ぶ。

### Terraformの作法（この回で増えたもの）
- [ ] **同じモジュール内は直接参照・別モジュールは `var.`** ｜芯：`aws_db_subnet_group.xxx.name` は同一モジュール内なので直接見える（**参照の境界はファイルではなくモジュール**）。`vpc_id` や `ec2_sg_id` は別モジュールにあるので変数で受け取るしかない。**`variables.tf` は外の世界との契約**であって、自分で作ったものを自分で使うのに契約は要らない。
  💬「db_subnet_group_nameしかないです、ネームとは？」
- [ ] **参照は「依存関係の宣言」でもある** ｜芯：`db_subnet_group_name = "portfolio-web-rds-subnet-group"` と直書きしても apply は通るが、**Terraformから見ればただの文字列で依存グラフに乗らない**ので、作成順序が保証されない。`aws_db_subnet_group.xxx.name` と書いて初めて「この2つには順序がある」と伝わる。
- [ ] **AWSリソースの参照はID/ARN/名前でバラバラ** ｜芯：VPC・サブネット・SGは**ID**、IAMロール・ALBは**ARN**、DBサブネットグループ・キーペアは**名前**。統一されていないのはサービスごとに別の時期・別チームが作ったから。**引数名の末尾（`_id`/`_arn`/`_name`）がそのまま答え**。
- [ ] **命名規則は層によって答えが違う** ｜芯：Terraformのリソースラベル・変数名は `snake_case`（HCLの慣習・AWSには送られない内部識別子）、AWSに渡す `name` は `kebab-case` に寄せる（DNS名になり得る）、**DB名はアンダースコアのみ**（ハイフン不可）。**「全部ハイフン」も「全部アンダースコア」も成立しない**ので、原則は「名前は使われる先の規則に従う」。`replace(var.project_name, "-", "_")` で使い先に合わせるのが第2回以来の組み込み関数の出番。
  💬「というかアンダーバーをやめたほうがいい？」
- [ ] **`-auto-approve` は「確認を捨てる」、planファイルは「確認を前倒しする」** ｜芯：実務は `terraform plan -out=tfplan` → 人間がレビュー → `terraform apply tfplan`。**レビューした内容と実行される内容が一致することが保証される**（`-auto-approve` だとレビューから実行までに状況が変わっても気づけない）。
  💬「-auto-approveはyesしなくても勝手にやっているということですよね」
- [ ] **applyは途中で失敗しても成功分はstateに残る** ｜芯：権限エラーで止まっても27個は記録済みで、再applyでは残り3個だけが作られる。**最初からやり直す必要がない**のが宣言型ツールの利点。
- [ ] **validateが通っても引数どうしの関係までは見ない** ｜芯：`password` も `manage_master_user_password` も書かない状態は、**構文としては正しいのでvalidateを通り、applyで拒否される**。第11回の「どの層で捕まるか」の続き。

### 名前解決と到達可能性（第9回・第10回の総復習）
- [ ] **RDSのエンドポイント名は世界中の誰でも引ける** ｜芯：実機でGoogleのDNS（8.8.8.8）に問い合わせたら、**プライベートIP `10.0.2.185` が普通に返ってきた**。それでも `Test-NetConnection -Port 3306` は失敗する。**10.0.0.0/8 はRFC1918でインターネット上をルーティングされない**から。
- [ ] **守っているのは情報の秘匿ではなく経路の遮断** ｜芯：住所は公開されているが、そこへ至る道が存在しない。**「名前が漏れることを心配する設計」はそもそも筋が悪い**。ALBとRDSの違いは「DNS名を持つか」ではなく「**返すIPがパブリックかプライベートか**」だけ。DNSは道案内をしただけで、道があるかは保証していない（L7の名前→L3のアドレス変換と、L3のルーティングは別問題）。
- [ ] **private EC2 が `dnf install` できるのはS3 Gatewayエンドポイントのおかげ** ｜芯：AL2023のリポジトリはS3の上にある。第9回で作ったGatewayエンドポイントがルートテーブルに経路を足しているから、NAT無しで届く。**第10回で `Hello from ip-...` が表示された時点で、その経路が生きている証明になっていた**。SSMエージェントは「AWSのAPIと会話する」ためのもので、パッケージは運ばない。
  💬「dnf install -y httpd のところだと、すでにインスタンス内に含まれているということ？」

## ⑮ 第13回で増えたネタ ─ 名前の層・運用の明示・ドキュメントの検証

### 名前は誰のものか（4つの層）
- [ ] **`endpoint` と `address` は別物** ｜芯：`endpoint` は `host:3306`、`address` はホスト名のみ。`mysql -h` に `endpoint` を貼ると**`:3306` まで含めた文字列をホスト名として名前解決しに行き失敗する**。JDBCのように `host:port` を1本で受け取る相手なら逆に `endpoint` が正解。**outputはAPIの戻り値なので、形は呼び出し側の都合で決まる**。
- [ ] **`identifier`（箱）と `db_name`（中身）は入れ子の別階層** ｜芯：`identifier` はDBインスタンス＝MySQLが動いているサーバーの名前でエンドポイントの先頭になる。`db_name` はその中に作られるデータベース1個。**決定的な証拠＝許される文字が正反対**（`identifier` はハイフン可・アンダースコア不可＝DNS名になるから、`db_name` はその逆）。だから `replace()` が要るのは `db_name` にだけ。
  💬「identifierについて、db_name となにが違うの？」
- [ ] **1つのRDSに複数のデータベースを置けるが、Terraformは1個しか作らない** ｜芯：`db_name` は文字列1個＝「作成時についでに1個作れ」という引数。2個目以降は `CREATE DATABASE`＝SQLの世界。**Terraformの管轄はAWSのAPIで作れるものまで**で、箱の中の構造（DB・テーブル・ユーザー・権限）はアプリの領分（スキーマ管理はFlyway/Liquibase＝ライフサイクルが違う）。実機の `SHOW DATABASES;` に5個出たうち、自分が宣言したのは1個だけだった。
  💬「db_nameはRDB自体を指しているわけではないなら、テーブルは複数個つくれますよね、なのでdb_nameを複数おけるの？」
- [ ] **命名規則の議論が成立するのは「自分で決める名前」だけ** ｜芯：`multi_az` のような**引数名はプロバイダーが決めた固定の綴り**で、kebabかsnakeかという選択肢が存在しない。`multi-az` と書いて `validate` に `Did you mean "multi_az"?` と怒られた。自分で決められるのはラベル（snake）・AWSに渡す値（kebab）・DB名（snakeのみ）の3つ。**「命名を揃えよう」という良い意図が事故になる**典型。
  💬「kebab-caseとはなに？」

### 運用を名詞で書く（マネージドの責任分界点）
- [ ] **`maintenance_window` は「やるかどうか」でなく「いつやるか」** ｜芯：真偽値だと思って `false` と答えたが、実際は `"Mon:16:00-Mon:16:30"` という文字列。**パッチ適用は断れない**。書かなかった場合に起きるのは「メンテナンスされない」ではなく「**AWSが時間帯を勝手に選ぶ**」。マネージドで手放したのは実施の有無、手元に残っているのはタイミングだけ ─ だから引数が「いつ」を問う形をしている。
- [ ] **ウィンドウは「開始してよい枠」であって完了保証ではない** ｜芯：AWSも超過を明記している。だから**業務開始の直前に置いてはいけない**（「8時始業だから7:30-8:00」は危険）。そしてバッファが買っているのは「衝突しない保証」ではなく「**何分の超過まで耐えられるか**」という量 ─ backupを16:30開始にすれば0分、17:00開始なら60分の余裕。**余白は量として設計する**。
  💬「このwindowについて、時間を超えることはないのでしょうか、backup_windowにmaintenanceが割り込むとか」／「では17:00が被っているのはよくないってこと？」
- [ ] **メンテナンスの所要は種類で桁が違う** ｜芯：OS/ホストのパッチ＝数分、エンジンのマイナー更新＝10〜30分、メジャー更新＝30分〜数時間（かつ自動では走らない）。`db.t3.micro`・10GB・検証データだけの構成なら数分〜十数分で、**60分のバッファは正直過剰**。**設計判断は規模に依存する**ので、「この規模なら不要ですよね」と突かれたら**過剰だと分かった上でやっていると答えられるか**が分かれ目。適用待ちは `aws rds describe-pending-maintenance-actions` で事前に見られる。
  💬「実際にはどうなのですか、メンテナンスの時間はどれくらいかかるの？」
- [ ] **書式が頻度を表現している** ｜芯：`maintenance_window` は曜日あり（週1回）、`backup_window` は曜日なし（毎日）。**毎日実行される物に「月曜」と書く場所は要らない**。引数名が似ているので同じ形だと思い込むと弾かれる。時刻はどちらもUTCなので **+9してJSTに戻して確認する**（`Mon:16:00` UTC = **火曜** 01:00 JST ＝ 曜日もズレる）。
- [ ] **`backup_retention_period = 0` は「短い」ではなく「無効」** ｜芯：0にすると自動バックアップが止まり、PITRだけでなく**Multi-AZもリードレプリカも作れなくなる**。1と0の間には他の設定にない断絶がある。
- [ ] **可用性は単独で語らずコストとのトレードオフで語る** ｜芯：Multi-AZは待機系をもう1台立てるので**料金がほぼ2倍**。「可用性のため true」だけだとコストを考えたことがない人に見える。逆に `false` でも「稼働時間が短い学習環境なので要件が無い、本番ならRTO/RPO次第」と言えれば加点。**「いらない」ではなく「要件が無いから要らない」**。なおMulti-AZのスタンバイは読み取りに使えない（それはリードレプリカ）、価値はAZ障害対策だけでなく**毎月来る計画メンテのダウンタイム短縮**にもある。
- [ ] **`multi_az = false` というコードは「知らない人」と見分けが付かない** ｜芯：判断の結果はコードに残るが、**判断の理由は残らない**。だから置き場所が要る ─ コミットメッセージの本文と、READMEの設計判断表。第11回の「コードは設計判断の記録」の続き。

### 変更できるかを決めるのはTerraformではなくAWS
- [ ] **`identifier` は in-place、`db_name` は replacement** ｜芯：AWSに `modify-db-instance --new-db-instance-identifier` があるので**リネームは可能**＝`~ update in-place`。一方 `DBName` は `ModifyDBInstance` に無いので `-/+ replacement`＝**データが消える**。直感と逆に「箱の名前」は変えられて「中身の名前」は変えられない。**見分け方はRegistryの `Forces new resource` の注記**。
- [ ] **`~ in-place` は「業務影響ゼロ」を意味しない** ｜芯：`identifier` をリネームするとエンドポイントのホスト名も変わるので、**接続中のアプリは繋がらなくなる**。Terraformの表示記号と業務影響は別の話。
- [ ] **ラベルの変更はAWSに1回もAPIを飛ばさない** ｜芯：リソースラベル（`rdb_subnet_group` → `rds_subnet_group`）はstateのキーが変わるだけなので `moved` で解決できる。`identifier` はAWSに送る値なので `moved` では解決できない。**「変更が届く先」が違う**。なお `moved` が要るのは既存stateがある時だけで、destroy後の空state中ならタダで直せる。

### 最新追従か再現性か（バージョン管理の一貫した構造）
- [ ] **`engine_version = "8.4"` はパッチ番号を書いていない** ｜芯：実機で立ったのは **8.4.9**。`.9` は一度も書いていない＝**AWSが選んだ**。書き方を `"8.4.9"` にすれば固定できるが、`auto_minor_version_upgrade`（既定true）と衝突すると**コードとの差分が直せない形で残る**。
  💬「engine_version = "8.4"（パッチバージョンなし）とはどういう事？」
- [ ] **AMIも同じ構造の判断をしている** ｜芯：`data "aws_ami"` の `most_recent = true` ＋ 起動テンプレートの `version = "$Latest"`。**`most_recent` を書いていること自体が「複数マッチする」ことの宣言**で、`data` は plan のたびに評価し直される。結果、**同じASGの中でAMIの世代が混ざりうる**。この構成は AMI とエンジンの2か所とも「最新追従」を選んでいるので、**一括で「パッチ適用の自動化を優先し再現性を犠牲にしている」と説明できる**。
- [ ] **パッチを当てる理由は「脆弱性が公開されるから」** ｜芯：修正がリリースされると**何が直ったかも同時に公開される**（CVE）。つまり未適用のシステムは**攻撃方法を攻撃者に教えている状態**になり、危険度が時間とともに上がる。
  💬「パッチをあてて必ず新しいバージョンにしておく必要性はなに？」
- [ ] **「固定 vs 追従」は二択ではない** ｜芯：AWSはサポート切れのエンジンを**強制的にアップグレードする**ので、固定は永続できない（第12回でMySQL 8.0のEOLを自分で調べたのがこれ）。実務解は**固定＋定期更新プロセス**＝「誰がいつ上げるかを決める」問題。**固定は放置と同義になりやすい**ので、固定するなら更新を回す仕組みとセットにする。
- [ ] **t2とt3ではクレジット枯渇時の挙動が違う** ｜芯：t2はstandardが既定＝性能が落ちるだけ、**t3はunlimitedが既定＝性能を維持する代わりに追加課金**。`credit_specification { cpu_credits = "standard" }` で明示できる。「AWS任せの既定を知った上で選ぶ」の一例。

### ドキュメントとポートフォリオ
- [ ] **ドキュメントには `terraform validate` が無い** ｜芯：コードの誤りはTerraformがどこかの層で捕まえてくれるが、**READMEの誤りは誰も捕まえてくれない**。読んだ人が詰まるだけ。「誤りが捕まる層」の一番外側にあるのがドキュメント。
- [ ] **ドキュメントのドリフト** ｜芯：READMEが3回分コードから遅れていた。**自分でドリフトを洗い出して直せる**のは実務スキル（「READMEを信じて手順を打ったら動かない」は日常的に起きる）。視点は3つ ─ ①追加された物が書かれていない ②書いてあることが古い ③手順が足りない。
- [ ] **表は「語りたい判断」・コードは「した選択の全部」** ｜芯：面接官は表だけ見て質問せず、**コードを開いて「なぜ `t2.micro` なんですか」と聞く**。表に載っていない＝答えなくていい、にはならない。だから必要なのは**表に無い選択を洗い出して答えを用意する検品**。実際に6問出して正答3・誤答3（AMI非固定／Golden AMI／t2の理由）だった。
  💬「自分が危惧しているのはここに記載されていない設計判断のことです」
- [ ] **「特に理由はありません、今なら変えます」は減点にならない** ｜芯：`t2.micro` を選んだ理由を調べたら**理由が無かった**（t3の方が新世代で単価・性能とも有利）ので t3 に変更した。**取り繕った理由を答えて突っ込まれる方がずっと悪い**。
- [ ] **既知の制約を書くべき4つの理由** ｜芯：①面接官は必ず穴を探し、見つける ─ 書いてあれば「把握している人」、無ければ「気づいていない人」で**同じ穴が正反対の評価になる** ②**制約ゼロは「完璧」ではなく「棚卸ししていない」と読まれる** ③書いた項目を聞かれれば準備した答えが出せる＝**質問の主導権を取れる** ④READMEの「なぜその構成にしたかを説明できることが目的」という宣言と矛盾する。**書き方は「できていない」ではなく「意図的に後回しにした、理由はこれ」**にする（TODOリストではなく優先度判断の記録に）。
  💬「それを嫌う人もいますが、私は書くべきだと思っています→理由は？」
- [ ] **手順書は実行して初めて検証される** ｜芯：READMEに書いた確認手順を自分で実行したら、**mysqlのプロンプトにPowerShellのコマンドを打ち込んでいた**。ローカル→SSM→mysql の3階層から抜ける手順（`exit` 2回）を、書いた本人が書き忘れていたから。加えて `Test-NetConnection` はPowerShell専用でMac/Linuxでは動かない。**書いた側は分かっているつもりでも、読む側は上から順に実行する**。
- [ ] **面接で喋る文章だけは自分で書く** ｜芯：判断基準は「**面接で口から出す必要がある文章か**」。設計判断表は必ず自分で書き、Mermaid図やコマンド手順は書いてもらってよい。**人の言葉で書いた表は、聞かれたときに喋れない**。ただし「誰が書いたか」自体は問題ではなく、実務でもドキュメントは他人が書く ─ 問題は**自分が説明できない記述が自分の名前で公開されること**なので、必要なのは書き直しではなく**検品**。
  💬「READMEはこちらで編集したほうがいいの？」／「というか気になるのは今までの部分です、基本書いてもらってたのでこれでいいのかわからない」

### git ─ コミットの粒度とメッセージ
- [ ] **件名＝何をしたか／本文＝なぜしたか** ｜芯：`git commit -m "..."` は件名だけを書いた形。`-m` を複数書くと2つ目以降が本文の段落になる（**1つ目が件名**）。`git log --oneline` に並ぶのが件名＝目次、本文は開いたときだけ読まれる。
  💬「本文はありますか？」
- [ ] **本文は毎回書くものではない** ｜芯：判断基準は「**差分を見れば分かることしか無いなら件名だけでいい**」。typo修正やリネームには不要で、**選択肢が複数あって片方を選んだとき**（`multi_az = false`）に書く。実務ではPull Requestの説明欄に書くチームも多いが、**判断の理由をコードの外に残す**という発想は同じ。
  💬「いままで書いてきてなかったが書くのが普通という事？」
- [ ] **件名が書けないときは、コミットの切り方が悪い** ｜芯：READMEのRDS反映（データ層）と `instance_type` 変更（計算層）を1つのコミットに入れたら件名が決まらなかった。原則は**1 commit = 1つの論理的な変更**。ただし同一ファイル内に混ざると分離が面倒なので、**後から分けるより作業の途中で区切る方が圧倒的に楽**。
- [ ] **件名はdiffで一番大きい変更を代表させる** ｜芯：119行の変更のうち一部しか件名に書かないと、`git log --oneline` を追った人が**そのコミットを見つけられない**。push前ならローカルなので `git commit --amend` で直せる。
- [ ] **`git add .` と `git add -A` の違いは範囲** ｜芯：`.` はカレントディレクトリ以下、`-A` はリポジトリ全体。ルートで打つなら同じ。`-u` は追跡済みファイルのみ（新規は入らない）。Git 1.x の頃は `.` が削除を拾わなかったが2.0以降は拾う。
  💬「git add -A と git add . の違いとは？」

### ネットワーク ─ プライベートアドレスと名前解決
- [ ] **`nslookup` は「名前をIPに変換する」だけで接続しない** ｜芯：`nslookup` は成功し、`Test-NetConnection` は失敗する。**この2つが別の段階**だというのが今回の証明の核心。なお `Test-NetConnection` の出力にある `RemoteAddress` が名前解決の結果なので、実は別途 `nslookup` を打つ必要すらない。
  💬「nslookupとは？」
- [ ] **RDSにパブリックIPは存在しない ─ 公開されているのは「名前」** ｜芯：`publicly_accessible = false` なのでパブリックIPは付与されていない。公開されているのは**ホスト名とDNSレコード**で、返る値はプライベートIP。`publicly_accessible` が制御しているのは**パブリックIPを持たせるかどうか**であって、名前の公開ではない ─ **「公開する」＝到達可能なアドレスを持たせること**。
- [ ] **自宅LANもVPCも同じRFC1918の「別々の島」** ｜芯：`Test-NetConnection` の `SourceAddress : 192.168.13.174` は**自宅ルーターが配ったLAN内アドレスで、公開IPではない**（外に出るときルーターがNATで付け替える／公開IPは `curl ifconfig.me` で見る）。RFC1918の3範囲は `10.0.0.0/8`（企業・**VPC**）・`172.16.0.0/12`（Docker等）・`192.168.0.0/16`（家庭用ルーター）で、**インターネットで使われないので世界中で重複している**。`vpc_cidr_block = "10.0.0.0/16"` と書いた1行の意味＝**AWS上に作った自分専用のプライベートネットワークの島**。繋ぐにはVPNやDirect Connectで明示的に道を作る必要がある。
  💬「SourceAddress : 192.168.13.174はなんですか？インターネットの公開IPではないの？」
- [ ] **壁は2枚ある** ｜芯：①経路が無い（今回 `Test-NetConnection` で確認したのはここ）②仮に①を越えても `rds_sg` が `ec2_sg` からの3306しか受け付けない。**片方の設定を間違えても、もう片方が残る**＝設計判断1の多層防御がデータ層でも同じ形になっている。
- [ ] **CloudWatchはコンソールの一部ではない** ｜芯：マネジメントコンソールは**AWSを操作するWeb UI＝見る手段**、CloudWatchは**メトリクス・ログ・アラームを持つ独立したサービス＝見られる対象**。同じデータにCLIやSDKからも到達できる（`aws cloudwatch get-metric-statistics`）ので、「コンソール上のCloudWatch」という入れ子は成立しない。**IaCをやっている人ほど、ここの言い分けが効く**。
  💬「CloudWatch はコンソールの一部ではありませんとはどういう事？」

## 全体を通じて言語化できるようになったこと
- 「値の決定権を誰が持つか」で variable / data / locals / resource を説明できる
- `count`（インデックス）と `for_each`（キー）の設計上の違い
- `moved` と依存グラフ、無停止リファクタリング
- 「モジュール = 関数」という一貫したメンタルモデル
- コード（git）と state（リモートバックエンド）の責務分離
- IAMのアイデンティティ／リソースベースの違い、ARNの構造
- 「動いた」で止めず、`validate` が通っても誤りは残ると疑える姿勢
- Terraformが管理する境界（宣言＝名詞）と、運用操作（実行＝動詞）の線引き
- 可用性は障害の排除ではなく検知・復旧時間の最小化であり、速い検知と誤検知はトレードオフだということ
- ポート番号は代理指標にすぎず、経路（L3）・封筒（L4）・中身（L7）を分けて説明できる
- セキュリティグループを「誰が接続を開始するか」から機械的に導ける
- ヘルスチェックは「インスタンスを殺す引き金」であり、殺して直る問題だけを見るべきだということ
- URLのパスとファイルシステムのパスは別の空間で、両者を繋いでいるのはWebサーバー内部の翻訳ルールにすぎないこと
- 既定値を明示してもインフラは変わらないが、コードが「設計判断の記録」に変わるということ
- 「ステートフル」がSG（通信の記憶）とリソース（データの保持）で別物であり、混同すると設計判断を誤ること
- 機密は「守る」より「そもそも持たない」方が確実であり、それを実現する手段がマネージドサービスとの統合であること
- IAMの必要権限は静的には洗い出せず、実行しながらCloudTrailで確定させるしかないこと
- 名前解決と到達可能性は独立で、privateなリソースは「隠れている」のではなく「経路が無い」だけだということ
- 「名前」は層ごとに持ち主が違い、命名規則を選べるのは自分が決める名前だけだということ
- マネージドサービスで手放したのは「実施の有無」で、手元に残っているのは「タイミング」だけだということ
- ある設定を変更できるかを決めるのはTerraformではなくAWSのAPIであり、それはドキュメントで事前に確認できること
- バージョンの「固定 vs 最新追従」は二択ではなく、「誰がいつ上げるかを決める」問題だということ
- ドキュメントには validate が無いので、手順書は自分で実行して初めて検証されるということ
- 設計判断の表は「語りたい判断」にすぎず、コードに書かれた選択はすべて質問の対象になるということ
